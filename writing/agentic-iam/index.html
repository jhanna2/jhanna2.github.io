Status: early research. Sixteen hypotheses are written down. A small reference implementation tests the structural claims behind three of them; everything else is designed and nothing has been tested empirically.

Why this matters to the argument

In the essay I argue that when attacker capability stops varying, priority depends on three things: reachability, current capability and blast radius. A defender cannot move the capability term. Reachability and blast radius are ours to shrink. For autonomous agents, our own and anyone else's, that means deciding what an agent may touch, for how long, and how much damage it can do before something stops it. This piece describes one design for that and the claims it rests on.

Start here: the minimum viable version

The design has many layers. You should not build most of them first. I would begin with an inventory of access: for each resource, what reaches it and how (a standing key, a service account, an OAuth grant, a human session), which agents already touch it, whether it lives in a cloud, a SaaS product or your own code, how critical its data is, and which of its actions can do damage on their own.

Then build four things in one low-criticality area. Short-lived tokens replace the standing keys. A task envelope limits a token to the signed task and the plan the agent committed to. A broker sits between the agent and the credential, so the agent never holds one. An audit log records every grant, and doubles as the evidence for every later decision. When that slice works, move it to where agents already touch critical data, because that is where the risk is today. Add the other layers when a trigger says you need them: a decomposed broker when it fronts critical resources, an enforcing proxy when a critical SaaS product only offers coarse credentials, drift budgets when agents do bulk work.

Four control points

Agent access is a pipeline: issuance, delegation, execution and monitoring. Most failures I have seen described come from hardening one point and neglecting the others. A well-scoped token does nothing if the agent spawns a sub-agent with a wider one. A tight issuance check does nothing if nobody watches what the agent does with the token for the next ten minutes.

The core problem with model-written roles

Human roles are coarse because nobody can author a permission per action. Agents are cheap to issue for, so a model can draft a narrow scope at request time. That solves the authoring problem and creates a new one: the model doing the drafting becomes the highest-value target in the system, and an injection aimed at the scope request is worth more than one aimed at the task.

The answer is to take authority away from the model. A human writes a ceiling for each class of agent. A model proposes a scope as structured data. Code checks the proposal against the ceiling and the signed task and either issues or refuses. Models judge only what code cannot: whether a well-formed plan serves the stated goal. They can raise a request to a human but never approve one. If every checker model fails the same way, the cost is a missed flag inside bounds that code already enforces, not a grant outside them.

A natural objection is that scoping a write to one row seems to require knowing every row of every table. It does not have to. The synthesizer sees a catalog of resources, with names, classes, owners and the scope parameters each accepts, and never the data. It scopes by predicate tied to the task, such as "rows for customer A", and the resource's own layer resolves it. Resource owners publish the templates, so each domain's synthesizer knows only its own. Anything without a template is denied. I treat this as a hypothesis, because the open question is how much a template language can say before owners stop writing templates.

Micro-privilege and bounded drift

Because agents are cheap, a task can be broken down until each agent holds almost nothing: write one value, read one row, run one query. A million records is a million sub-agents. The limit that matters is how far an agent strays from its plan, not how much it touches. An agent meant to update one customer that touches fifteen others has drifted by fifteen. The envelope carries drift budgets, and crossing one stalls the agent and revokes its tokens. Budgets are carved out of the parent's across delegation, never copied, so ten thousand sub-agents cannot add up to the whole database.

The result is a blast radius you can design to. A compromised agent exposes roughly its drift allowance before it stops. Drift is also an operating cost: wasted calls, retries, wrong permissions and slower products all show up as the same measurements, so the same counters serve security and finance.

The broker as a control plane

A broker that holds every key, the budget ledger and the audit trail is one compromise away from yielding all three. I would split it the way Kubernetes splits admission, control and audit: a minter that turns approved grants into short-lived tokens and holds no model; a decider that applies policy and never holds a key; a ledger that only counts; and an append-only audit store in a separate trust domain. The decider answers with graduated responses: allow, allow narrowed (masked results, a smaller breadth, a shorter life), or escalate. A model may narrow a grant but never widen one.

Two features matter more than they look. A feasibility reviewer that can only alert compares the task's goal with what is currently permitted, so a decider that denies too much shows up before the business routes around it. And canary requests mixed into live traffic test the decider continuously: one that treats canaries differently has drifted or been compromised.

When the resource cannot enforce it

Fine-grained tokens only help where the resource accepts them. I sort resources into four tiers. Some support native narrowing (cloud session policies, downscoped tokens). Some are yours, and enforcement can sit at the resource, keyed on the grant (row-level security, views per task class). Some are coarse SaaS products, where an enforcing proxy holds the service-account key and agents hold a narrow token valid only at the proxy. Some cannot be proxied, and the only control is that every action in the vendor's own log must reconcile to a grant, with those resources kept out of autonomous reach.

The proxy has weaknesses worth naming. Per-API adapters break when vendors change formats. Response filtering is harder than request filtering. And the team that owns the SaaS relationship can usually mint another key and build around the proxy, usually for good reasons and usually to move faster. I treat that team as an adversary class of its own and measure a bypass rate: the share of vendor audit events with no grant ID. The durable defense is making the sanctioned path less work than the shortcut. Vendors adopting downscopable tokens would shrink the problem. Token exchange (RFC 8693, January 2020) and rich authorization requests (RFC 9396, May 2023) already exist as standards; the gap is adoption.

People, policy and failure

At agent scale nobody approves individual requests. If they try, they approve to make the prompts stop. The human tier works only as a budgeted resource: escalations go to the data owner, only irreversible actions on critical assets reach a person, each approver has a daily budget, approvals require reading something only the request reveals, and known-bad canaries test whether approvers catch them. A timeout on a critical action denies.

Response actions need their own rating. Quarantining a host or disabling an account can do more damage than any read, and the damage does not track the asset's data criticality. Isolating a low-value host that runs an essential service is still an outage. I rate actions separately, cap the number of targets, expire the action unless someone confirms it, and require a human for critical targets.

Since people govern policy rather than requests, the policy is what an attacker goes after, along with plain entropy. It lives in version control with review, compared against a pinned baseline so a slow widening shows up as one change. Fail-safe controls are also switches someone outside can flip: planted data pushes legitimate tasks over their budgets, an escalation flood times approvals out. The failure mode is a matrix, not a default. Reads fail open, writes and egress fail closed, adjusted by criticality and whether the service is essential, and the failure state is a narrowed mode instead of a halt, so an essential service keeps working while someone investigates.

Fitting an existing IAM estate

This sits on top of an identity provider, human single sign-on, privileged access management and cloud IAM. It does not replace them. Cloud IAM becomes the ceiling and the first enforcement tier. What it replaces is the standing agent credential. Agents are workloads, so their identity lives in the same federation, and hardware-rooted attestation ties it to a measured platform instead of a secret handed to the agent.

It also depends on programs that may or may not exist: data classification, an asset inventory with owners, network egress control, logging that can be reconciled, secrets management, change review, third-party risk management and incident response. Where one is missing, the design degrades in a known way. Without classification, criticality is set by hand and goes stale. Without egress control, the proxy is advisory. I would choose the first area to deploy by readiness as well as risk.

Cost

The obvious objection is that a model writing scopes all the time costs too much. Most of the work is code: the ceiling, the envelope, budgets, lineage checks. Models see only the residue. Synthesis happens once per class of task, and each request instantiates the template with code. The likely largest cost is people's time, which is why it is budgeted. I have a cost model with named variables and a hypothesis to measure them. I do not have measurements, so I quote no figures.

What is built

About 230 lines of Python model three of the structural claims: a scope language with a conservative "within" check and a compiler that refuses any proposal outside the ceiling; capability tokens built on the macaroon construction (Birgisson et al., NDSS 2014), where anyone can add a restriction and nobody can remove one; and the carved-budget ledger. I wrote a proof sketch for each and twelve randomized and exhaustive tests. None found a widening, a forged token or a subtree overspend, and three deliberate bugs I planted were each caught. This shows the logic holds in a model I wrote. It does not show that real cloud policy languages have a clean subset relation, which is the main risk to the compiler claim, and it measures no latency. The tokens as written need the verifier to hold the root key; a public-key variant is future work. Nothing else here is built.

What would change my mind

The claims are written as hypotheses with falsifiers. Examples:

  • If catalog-only synthesis produces scopes materially worse than synthesis with full data access, the template idea fails.
  • If red teams cause outages through the controls about as easily under the fail-mode matrix as under uniform fail-closed, the matrix does not help.
  • If a large share of decisions still needs a model after the deterministic checks, the cost argument weakens.
  • If checkers with different inputs are no better than same-input checkers at catching injected escalations, the diversity argument weakens.

I will publish negative results.

Where it connects

Attested agent identity, the question of whether an agent is one of ours, is a candidate answer to the friendly-fire problem in the agentic tarpit: our own agents must tell real from decoy, and an attacker's must not. The open question is attesting the task an agent is doing, not only the agent. For the program that runs on top of all this, see CTI as code and the agent-first TIP.

The threat model and the hypotheses are kept in a private research repository. I will publish results, including negative ones, as they exist.
