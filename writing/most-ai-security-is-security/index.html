Most AI Security Is Security

Published 24 October 2026. Jeff Hanna.·5 min read
CONTENTS

This builds on the coding-agent research in this series, which I did from vendor documentation and haven't yet tested in a lab.

When I set out to compare the ways organizations try to control coding agents, I expected the AI-specific products to do most of the work: the vendor's enterprise plan, a model gateway, a prompt firewall. The comparison came out the other way. The controls that reached every agent, whichever vendor made it, were endpoint management, network egress rules and identity. None of them was built for AI. The AI-specific controls each covered one product, or one path to the model, and every one of them had a documented way around it.

I now think that's the general case. Most of the risk in an AI system comes down to questions security programs already know how to answer, and the bolt-on tools sit on top of those answers rather than replacing them.

The questions an AI system raises

Take an agent that reads a repository, calls a model and runs commands. The ways it can hurt you are these:

  • It can reach things through the identity it runs as
  • It can read data that nobody classified or restricted
  • It can send data to places the network lets it reach
  • It can run programs on a device whose configuration you don't control
  • It can use keys that sit in its environment

Each of those has an owner and a mature practice. Identity and access management decides what the agent's token can touch. Data classification and access policy decide whether the sensitive files are readable at all. Network segmentation and egress control decide where anything can go. Device management and endpoint detection decide what runs and record it. Secrets management decides which keys are in the environment and for how long.

Prompt injection is the case people treat as new, and the impact still runs through those same questions. An injected instruction can make an agent try anything. What it achieves is bounded by what the agent's identity can reach, what data it can read, and where it can send the result. An agent whose token can read one repository, with egress only to its model vendor and the package registry, gives an injection very little to work with. An agent running as a developer with broad cloud credentials and open egress gives it everything, and no prompt filter in front of it changes that much.

Where the bolt-on tools sit

The AI-specific products mostly watch the conversation: prompt and response filters, model gateways with content rules, AI security posture tools that read agent configuration, data loss rules tuned for prompts. They answer one question the fundamentals can't express, which is what the text going to the model says.

That question matters. It's also a narrow one. A content filter can't see the hook that ran beside the conversation or the credential the agent used, and it can't see where the data went after the model's answer came back. It makes a probabilistic judgment about text, and it can be fooled by the same kind of text it's judging.

So I'd order the work. Fundamentals first, sized to the agent: a workload identity with narrow scope, data that's classified and access-controlled before an agent can reach it, egress that names its destinations, managed devices, short-lived secrets. Then the AI-specific controls, for the residue the fundamentals can't express.

A useful question for any AI security vendor is what their product adds if your identity, data and network controls are already right. A good product has an answer. Many pitches assume those controls aren't right, and sell the product as a substitute for fixing them.

Why organizations go the other way

The fundamentals are slow. Narrowing identities, classifying data and segmenting networks are organizational changes with long queues, and they belong to teams that already have plenty to do. An AI security product can be bought this quarter and shows a dashboard next month. I understand the choice. I think it gets the order wrong, because the product then sits on a foundation that leaks underneath it.

Vendors make this worse. You can't throw a rock right now without hitting an AI or agent security company. I can't name a new one selling packet capture. Funding follows what's new, so the sales calls, conference talks and analyst reports all point at the AI layer, and the message a security leader hears is that AI risk needs AI products.

I think the older disciplines also feel close to done. Most organizations have an identity program, a data classification policy and a network design, and the people who own them would call them good enough. That's rarely true for the specific case of an agent with a broad token, but the feeling of done moves attention to the new thing.

Then there's the return on effort. Every discipline has diminishing returns. A team that spends a month on a ten-year-old identity design might remove a few standing permissions, and it looks like a small win. The same month spent on AI security, where nothing existed before, produces a policy, a tool and a dashboard, and it looks like a lot of progress. The newer the area, the more visible work each hour buys. But the small win in the old design may cut more real risk than everything built in the new one, because the agent's reach runs through it.

There's also a reporting effect. "We deployed an AI firewall" is a sentence leadership can repeat. "We cut the agent's token scope from the whole cloud account to one bucket" sounds like routine work, and it's the change that limits what an attacker gets.

Where AI-specific controls earn their place

Some risks have no classic precondition, and that's where I'd spend on AI-specific work.

Training data poisoning is the clearest. A backdoor planted in public web text that later lands in a training set never touched your identity system or your network. Research published in October 2025 by Anthropic, the UK AI Security Institute and the Alan Turing Institute found that around 250 poisoned documents were enough to plant a simple backdoor in models from 600 million to 13 billion parameters, regardless of how much clean data they trained on. Defending against that takes data provenance, evaluation and behavior monitoring, which are AI-specific practices.

Model behavior is another. A hosted model can change under you between one week and the next, and only evaluation will tell you whether it still does the job and still refuses what it should.

Even there, the fundamentals come back in. The training data store needs access control and integrity checks. The weights need custody. The evaluation pipeline needs to be something an attacker can't edit.

How confident I am

High for agent and application risks: identity, data, network and endpoint controls bound most of what an AI system can do, and that follows from where the system acts. Medium for the claim that organizations get the order wrong, which comes from vendor messaging and public discussion rather than any survey.

What would change my mind is an attack class against deployed AI systems that succeeds with narrow identities, classified data, controlled egress and managed endpoints all in place, and that only an AI-specific tool stops. I'd expect such cases to come from the model itself (poisoning, backdoors, behavior drift) and not from the agent's surroundings.
